# Ancestral Landing V2 --- Deployment and Rollback

## 1. Production architecture

The official production site is:

- `https://ancestral-col.com`

The frontend is deployed as static files to the Ancestral VPS and served
by Nginx.

Production path:

```text
/var/www/ancestral-col.com/
├── bootstrap/
├── current -> /var/www/ancestral-col.com/releases/<commit-sha>
└── releases/
    ├── <commit-sha>/
    └── ...
```

`current` is the path consumed by Nginx. Each deployment creates an
immutable release directory named with the Git commit SHA and switches
`current` atomically to that release.

The deployment keeps a maximum of 5 release directories.

The API is deployed independently at:

- `https://api.ancestral-col.com`

The Landing deployment must not modify the API Nginx configuration.

---

## 2. Production Nginx behavior

Landing root:

```nginx
root /var/www/ancestral-col.com/current;
index index.html;
```

Prerendered routes are resolved without a SPA fallback:

```nginx
location / {
    try_files $uri/index.html $uri =404;
}
```

Unknown routes must return a real HTTP `404`.

Custom 404 rendering:

```nginx
error_page 404 =404 /404.html;

location = /404.html {
    try_files /404.html =404;
}
```

This preserves the HTTP `404` status while rendering the Ancestral
`404.html` generated by the production build.

Do not replace this behavior with a fallback to `/index.html`, because
that would return Home content for unknown URLs and break the intended
SEO behavior.

## 3. Production CI/CD

Workflow:

```text
.github/workflows/production.yml
```

Production deployment is associated with branch:

```text
v2
```

The workflow runs quality validation for pull requests targeting `v2`.

A deployment can run only when:

- a commit is pushed to `v2`, or
- the workflow is manually dispatched from `v2`.

Manual runs from other branches must not deploy.

### Pipeline

```text
quality
  ↓
build
  ↓
artifact
  ↓
deploy
  ↓
production verification
```

The quality job runs:

```text
npm ci
npm run format:check
npm run lint
npm run test:run
npm run coverage
npm run build
SonarQube Cloud scan + Quality Gate
```

Deployment does not start unless the quality job succeeds.

## 5. Release creation and activation

The production artifact is built from `dist/` and packaged as:

```text
ancestral-landing.tar.gz
```

It is uploaded temporarily to:

```text
/tmp/ancestral-landing-<commit-sha>.tar.gz
```

The VPS deployment process:

1.  Creates a staging directory under `releases/`.
2.  Extracts the artifact.
3.  Verifies required files:
    - `index.html`
    - `404.html`
    - `robots.txt`
    - `sitemap.xml`
4.  Moves staging to:
    - `/var/www/ancestral-col.com/releases/<commit-sha>`
5.  Verifies the release files again.
6.  Records the previously active release.
7.  Creates a temporary `current.new` symlink.
8.  Atomically replaces `current`.
9.  Runs the production smoke test.
10. Removes old releases, keeping a maximum of 5.

The symlink replacement is atomic so Nginx never points to a partially
extracted release.

---

## 6. Automatic rollback

Immediately after switching `current`, the deployment checks the public
Home page and validates the production title.

If the smoke test fails:

1.  The workflow checks whether a previous release exists.
2.  It creates a temporary rollback symlink.
3.  It atomically restores `current` to the previous release.
4.  The workflow exits with failure.

A failed deployment must not be considered successful even when rollback
succeeds.

---

## 7. Manual rollback

Use manual rollback only when a deployed release must be reverted
outside the automated workflow. Prefer the non-root `deploy` account and
the permissions established for production deployment.

Connect to the VPS:

```bash
ssh deploy@2.25.117.32
```

Inspect available releases:

```bash
ls -lt /var/www/ancestral-col.com/releases
```

Inspect the current target:

```bash
readlink -f /var/www/ancestral-col.com/current
```

Select the known-good release:

```text
/var/www/ancestral-col.com/releases/<known-good-sha>
```

Validate that it contains the required files:

```bash
test -f /var/www/ancestral-col.com/releases/<known-good-sha>/index.html
test -f /var/www/ancestral-col.com/releases/<known-good-sha>/404.html
test -f /var/www/ancestral-col.com/releases/<known-good-sha>/robots.txt
test -f /var/www/ancestral-col.com/releases/<known-good-sha>/sitemap.xml
```

Activate it atomically:

```bash
rm -f /var/www/ancestral-col.com/current.rollback

ln -s   /var/www/ancestral-col.com/releases/<known-good-sha>   /var/www/ancestral-col.com/current.rollback

mv -Tf   /var/www/ancestral-col.com/current.rollback   /var/www/ancestral-col.com/current
```

Nginx reload is not required when only the `current` symlink target
changes.

Verify:

```bash
curl -I https://ancestral-col.com/
curl -I https://ancestral-col.com/servicios/ambientales
curl -i https://ancestral-col.com/deployment-smoke-test-not-found
```

Expected result for the final request:

```text
HTTP 404
```

with the custom Ancestral 404 document.

## 8. Post-deployment verification

The production workflow verifies:

- Home page title
- Servicios Ambientales title
- Servicios Forestales title
- Servicios Agrícolas title
- Manejo del Recurso Hídrico title
- Seguridad y Salud en el Trabajo title
- `robots.txt`
- `sitemap.xml`
- unknown URL returns HTTP `404`
- custom 404 title
- custom 404 page content
- `noindex,follow` on the 404 document

Production routes:

```text
/
 /servicios/ambientales
 /servicios/forestales
 /servicios/agricolas
 /servicios/recurso-hidrico
 /servicios/seguridad-salud-trabajo
```

The production site must not use an SPA Home fallback for unknown
routes.

## 9. GitHub Pages

GitHub Pages is a secondary deployment target and is not the canonical
production site.

Workflow:

```text
.github/workflows/deploy.yml
```

GitHub Environment:

```text
github-pages
```

Pages uses:

```text
/ancestral-landing/
```

as its base path.

The project provides:

```text
npm run build:pages
```

for the GitHub Pages build.

Production continues to use:

```text
npm run build
```

with base path `/`.

Canonical URLs and sitemap URLs must always use:

```text
https://ancestral-col.com
```

They must never be rewritten to the GitHub Pages hostname or
`/ancestral-landing/` path.

## 10. Security requirements

- Third-party GitHub Actions are pinned to immutable commit SHAs.
- Production workflow permissions are limited to `contents: read`.
- SSH uses:
  - `BatchMode=yes`
  - `IdentitiesOnly=yes`
  - `StrictHostKeyChecking=yes`
- The trusted VPS host key is stored in `VPS_SSH_KNOWN_HOSTS`.
- Production deployment uses the non-root `deploy` user.
- API deployment and Landing deployment share the current automation
  SSH key, but remain independent workflows and server configurations.
- The previous deployment public key should be removed only after both
  API and Landing deployments are confirmed working with the current
  key.

---

## 11. Operational notes

- `bootstrap/` exists only to provide a valid initial target before
  the first real release.
- After the first successful production deployment, `current` points
  to a release directory.
- Do not manually edit files inside a deployed release.
- A production change must be delivered through a new release.
- Do not delete the currently active release.
- Do not modify Certbot-managed SSL directives unless certificate
  configuration itself is intentionally being changed.
